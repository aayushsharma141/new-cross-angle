## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Operator terminal -> production Supabase | Privileged writes |
| Operator shell -> transcript/clipboard | Secret values can leak into logs |
| Edge functions (new code) -> production data | First deploy of previously undeployed functions |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-40-24-01 | Information disclosure | Secret values pasted into repo, chat or evidence files | mitigate | Runbook uses shell variables; verify SQL selects names only; Task 1 acceptance greps for hex strings; evidence files record names/statuses only |
| T-40-24-02 | Denial of service | Deploying functions/secrets breaks working Telegram alerts | mitigate | WEBHOOK_SECRET deliberately not changed here; old trigger and token keep working until plan 40-25 |
| T-40-24-03 | Tampering | `supabase db push` applies unrelated historic migrations | mitigate | Runbook and plan forbid it; single-file apply + migration repair only (ADR 0003) |
| T-40-24-04 | Elevation of privilege | Newly deployed handle-new-lead / stale-lead-checker callable by anon | mitigate | In-code bearer checks (plans 40-05/40-07); Task 3 step 5 proves 401 without a bearer |
| T-40-24-05 | Denial of service | Migration locks or fails mid-way | mitigate | Each migration is one transaction and idempotent; rollback table in the runbook; read-only pre/post checks |
| T-40-24-06 | Spoofing | Service-role key stored in Vault could be read by anyone with Vault access | accept | Same trust level as the service key itself; follows the existing runbook pattern |
| T-40-24-SC | Tampering | npm/pip/cargo installs | accept | No packages |
